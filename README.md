# Wraex

A native Rust rewrite of [Awakened PoE Trade](https://github.com/SnosMe/awakened-poe-trade)
(PoE1) and [Exiled Exchange 2](https://github.com/Kvan7/Exiled-Exchange-2) (PoE2),
with a [Rune](https://github.com/anomalyco/rune) UI.

Both originals are Electron + Vue apps that parse the item text you copy in game,
build a trade-site query and show price results in an overlay. Wraex keeps that
behaviour and drops Electron, with one game-agnostic core shared by both games.

**Status: pre-alpha, repo skeleton.** No parsing, trade or overlay code is ported
yet. The roadmap and the reasoning behind it are in [PLAN.md](PLAN.md).

## Layout

```
rust/                    Cargo workspace (all Rust code)
  crates/core/           game-agnostic types: item model, trade queries, API client
  crates/game/           the trait each game implements
  crates/poe1/           PoE1 parser and data, ported from ref/apt
  crates/poe2/           PoE2 parser and data, ported from ref/ee2
  crates/platform/       window tracking, overlay, hotkeys, clipboard, logs
  crates/app/            the Rune desktop app (binary: `wraex`)
  crates/golden/         loads the fixtures for Rust tests
ref/apt/                 git submodule: SnosMe/awakened-poe-trade (PoE1 reference)
ref/ee2/                 git submodule: Kvan7/Exiled-Exchange-2 (PoE2 reference)
tools/golden/            fixture harness that runs the TypeScript reference code
tools/package/           builds a release: binary + the assets it reads at runtime
fixtures/<game>/<case>/  golden fixtures: input.txt, options.json, parsed.json, presets.json, trade/
```

The TypeScript apps are never merged into this repo. They are pinned checkouts that
produce reference output; the Rust port matches that output exactly.

## Developing

Everything (Rust 1.99.1, Node 24, Python, `cargo-xwin`) comes from Nix/devenv:

```sh
devenv shell                 # dev shell
devenv tasks run check:all   # fmt + clippy + tests + Rune pin check
```

Without devenv, any Rust 1.99.1 toolchain works for the crates in `rust/`.
The Node version matters for the reference apps: EE2's CI uses Node 24.

```sh
cargo run --manifest-path rust/Cargo.toml -p wraex-app      # or: cd rust && cargo run -p wraex-app
cargo test --manifest-path rust/Cargo.toml --workspace
```

Checkouts are shallow. Clone with submodules, or fetch them later:

```sh
git clone --recurse-submodules <url>
git submodule update --init --depth 1
```

`devenv tasks run ref:apt:latest` moves the PoE1 reference to upstream master;
`EE2_TAG=v0.16.3 devenv tasks run ref:ee2:release` moves the PoE2 reference to a
release tag. Either way, bumping a reference is how drift shows up: regenerate the
fixtures and diff them.

## Packaging a release

A development build reads the game data, images and tray icon from the `ref/`
checkouts. A release ships those files beside the binary, so it runs wherever it is
unpacked:

```sh
python3 tools/package/package.py                  # host target -> dist/wraex-<version>-<target>/
python3 tools/package/package.py --archive zip    # plus dist/wraex-<version>-<target>.zip
```

The app looks for `assets/` next to its executable (or `Contents/Resources/assets` in
a macOS bundle); `WRAEX_ASSETS` points it at another directory. `assets/<game>/` holds
the reference's `data/<lang>/`, `images/` and `icon.png`, and `licences/` the notices.
`.github/workflows/release.yml` runs the script on Windows and Linux for a `v*` tag
and attaches the archives to a draft release.

## Porting rules

1. The JavaScript version is the spec. A module is ported when its output matches
   the fixtures byte for byte.
2. Prove the platform before porting features: overlay, hotkeys and clipboard are
   tested on Windows first (phase 2).
3. Keep the Rune rev in `rust/Cargo.toml` pinned, together with the same rev in the
   `[patch.crates-io]` table for the crates Rune vendors; bump them deliberately.
4. Static game data stays as generated by the two upstream projects for now, behind
   the game/data trait so it can be replaced later.
